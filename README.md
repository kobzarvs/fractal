# Burning Ship — Rust / WASM + GPU

Локальный исследователь фрактала Burning Ship с глубоким увеличением, маршрутами и встроенной проверкой точности/скорости. CPU-часть написана на Rust и компилируется в WebAssembly, параллельный расчёт пикселей остаётся в WebGL2.

## Запуск

Нужен Node.js 24+; основной режим требует WASM SIMD, WebGL2 и OffscreenCanvas worker в современном Chromium:

```sh
npm ci
npm run dev
```

Откройте http://127.0.0.1:5173/?route=western-armada&iter=16384&zoom=10

Готовый WASM SIMD-файл включён в репозиторий. Для его воспроизводимой пересборки нужны Rust, target `wasm32-unknown-unknown` и Binaryen (`wasm-opt`):

```sh
rustup target add wasm32-unknown-unknown
npm run build:wasm
npm test
npm run test:rust
npm run build
npm run preview
```

Проверенная цепочка сборки: Rust 1.98.1, Binaryen 132, Node 24.13.0. `npm run build` проверяет TypeScript и собирает приложение с готовым WASM-файлом; после изменения Rust сначала выполняйте `build:wasm`.

## Публикация на Vercel

Production: [burning-ship-wasm-gpu.vercel.app](https://burning-ship-wasm-gpu.vercel.app/?route=western-armada&iter=16384&zoom=30). Проект Vercel: `divers-projects/burning-ship-wasm-gpu`.

В `vercel.json` заданы Vite, установка через `npm ci`, сборка `npm run build` и каталог `dist`. Используйте Node.js 24. Готовый WASM включён в `public/wasm`, поэтому Rust на сервере сборки не требуется. Для `.wasm` настроены MIME `application/wasm` и перепроверка кэша при следующем запросе.

```sh
npx vercel login
npx vercel link
npx vercel --prod
```

После первой привязки достаточно `npx vercel --prod`. Локальный каталог `.vercel` исключён из Git. Публикация через CLI включает текущие файлы рабочей копии, в том числе ещё не закоммиченные изменения.

## Управление и проверка

- Колесо масштабирует относительно курсора, перетаскивание перемещает камеру.
- «Начать полёт» ведёт к выбранной точке; ползунок сразу задаёт глубину маршрута. «Обзор» возвращает весь фрактал.
- Два движка: **WASM SIMD + GPU** по умолчанию и **JavaScript · исходные шейдеры** с исходным BigInt-расчётом. JS использует отдельную сохранённую копию исходных шейдеров Burning Ship и исходную политику кольцевого кэша; WASM — оптимизированный renderer. Число итераций и сэмплов AA задаёт пользователь. Разрешение соответствует реальному `devicePixelRatio` и автоматически не уменьшается.
- Крупный FPS слева сверху показывает частоту вызовов отрисовки за последнюю секунду во время движения. Готовый неподвижный кадр показывает 0 FPS: приложение перестаёт рендерить. При смене движка, скрытии вкладки и изменении разрешения измерение начинается заново.
- Кнопка «Проверить точность и скорость» показывает таблицу WASM SIMD / JS: медиану расчёта опорной орбиты в Worker, полное время запроса и FPS одинаковой анимации после прогрева. Движки измеряются последовательно и используют свои шейдеры. FPS ограничен частотой `requestAnimationFrame`; аппаратное GPU-время показывает стоимость самой отрисовки. Отчёт также проверяет совпадение чисел и пикселей и позволяет скачать JSON. GPU-время берётся отдельно из аппаратных timer queries, если расширение поддерживается.
- `npm run bench` выдаёт JSON CPU-бенчмарка в Node/V8. Это отдельное измерение, а не оценка FPS браузера.

## Реализация

`crates/fractal-core` вычисляет опорную орбиту целыми массивами разрядов, затем строит BLA-матрицы и Float32-текстуры. Signed shifts, дополнительная точность, fold/celtic и округления проверяются относительно независимого JS BigInt-эталона. В горячем цикле нет выделений памяти. Параметры ядра: 1–4096 бит, 1–65536 итераций; координаты ABI передаются десятичными строками целых чисел в масштабе `2^bits`.

В режиме WASM один worker владеет OffscreenCanvas/WebGL2 и одной WASM instance. Rust рассчитывает fixed-point камеру и полёт, орбиту/BLA, раскладку и обновление кольцевого кэша, temporal AA, параметры и последовательность draw-команд. JavaScript обслуживает UI, события/расписание браузера и вызовы WebGL; численный планировщик кадра в нём не исполняется. Орбита считается порциями по 128 шагов через MessageChannel, чтобы обрабатывать отмену и ввод между порциями.

Линейная память фиксирована: **initial = maximum = 256 MiB**. Она выделяется при запуске instance; нет resizable ArrayBuffer, роста памяти и пересоздания views в рабочем пути. GPU-текстуры занимают отдельную память: например, 4K-кэш может превышать 400 MiB. Постоянные Float32Array views непосредственно передаются в WebGL с srcOffset; промежуточных копий орбиты через JS/между worker и главным потоком нет. Это не означает zero-copy в видеопамять: загрузку на GPU выполняет браузер/драйвер. Отдельный compute-worker с transferable-массивами сохранён только для JS-режима и независимых сравнительных тестов.

`src/gpu/legacy` — зафиксированный оригинальный JS/GPU путь. `src/gpu/wasm-renderer.ts` — WebGL-мост нового ядра. Прежний `src/gpu/renderer.ts` используется как независимый эталон математического планировщика в differential-тестах и не выбирается как движок приложения.

GPU сохраняет direct / float perturbation / extended-range perturbation, BLA, rebase и палитру. WASM-режим вычисляет уровень BLA целочисленными масками и повторно использует чтение Celtic-текстуры. Temporal AA накапливает центрированные сэмплы, перепроецирует историю при движении и сбрасывает её при смене параметров. Кольцевой кэш автоматически работает во время полёта. В WASM-режиме плотность 1.5 сохраняется на больших экранах: угловые полосы раскладываются по нескольким блокам текстуры, искусственного лимита 24 млн texels нет. Ограничения размеров GPU и реальные ошибки выделения памяти включают полноразмерный fallback. В JS сохранены исходные шейдеры и исходная адаптивная плотность кэша; это адаптация оригинального renderer к нашему интерфейсу, а не копия всего исходного сайта.

Для ручной проверки восстановления главного canvas добавьте `&diagnostics=1` к URL и нажмите «Проверить восстановление GPU». Кнопка «Измерить глубокий полёт WASM» отдельно профилирует WASM на текущем размере canvas при увеличениях 10^30, 10^60, 10^90 и 10^115. Автоматический benchmark отдельно проверяет этот lifecycle, совпадение кадров после восстановления и отмену настоящих Worker-задач.

Rust выбран для управляемой линейной памяти, нативных тестов и предсказуемого ABI. WebAssembly здесь — цель компиляции, а не конкурирующий язык. Сравнительного теста Rust против MoonBit не проводилось.
