# Текущая метрика GPU FPS

Крупный счётчик в обоих режимах теперь показывает оценку частоты кадров, завершение GPU-команд которых подтверждено через WebGL `fenceSync`. Это **не частота показа кадров на экране**: fence не сообщает время presentation/compositor. Из-за пакетных подтверждений и дискретного опроса показатель также не даёт точного времени завершения каждого кадра.

После отправки кадров контрольные fence создаются не чаще раза в 100 мс, одновременно ожидаются не более восьми. Проверка выполняется обычно раз в 250 мс через `clientWaitSync(..., 0, 0)`, без блокирующего ожидания GPU. Fence подтверждает накопленный префикс кадров; неподтверждённые кадры остаются в очереди счётчика. Первая подтверждённая пачка, включая возможный догоняющий хвост, задаёт базу отсчёта и не выдаётся за мгновенный всплеск FPS. Дальнейшая оценка использует окно около секунды; при редких подтверждениях интервал расширяется. Подготовительные проходы кэша в этот счётчик не входят.

Свежесть состояния worker проверяется отдельно: после 1000 мс без нового сообщения `state`, при ошибке или завершении worker прежнее число заменяется на «—» при следующем обновлении HUD. Ответы на snapshot и исходящие команды свежесть не продлевают. HUD обновляется отдельным таймером с периодом 250 мс и не зависит от продолжения canvas rAF. Браузер может задерживать и таймер; при полной остановке главного потока обновить DOM невозможно. Реализация: [GPU completion](../src/gpu/frame-completion.ts), [runtime client](../src/runtime/client.ts).

**Все исторические показатели «FPS» ниже, включая таблицы и проценты изменения FPS, измеряли отправку render-команд. Они не являются измерениями подтверждённых GPU-кадров или кадров, показанных на экране.** Исторические числа и исходные JSON сохранены; их нельзя напрямую сравнивать с новым крупным счётчиком GPU FPS. Встроенная таблица этих старых измерений теперь подписана «Отправка кадров», с единицами «кадр/с». Отдельные измерения CPU-времени и аппаратных GPU queries сохраняют прежний смысл.

# Исторические замеры: исправление старта и срыва кэша — 25 сентября 2026

Подтверждены две проблемы планировщика. Холодное заполнение ограничивалось половиной экранного числа samples за кадр, а при 25 FPS камера открывала больше новых строк, чем успевало заполниться. После подготовки кэша один кадр длительностью 80–100 мс мог снова включить этот режим: настоящий WASM в тесте выдавал ещё 473–474 кадра с одновременными ring fill и fullscreen fallback за следующие 20 секунд.

Теперь WASM заранее заполняет кэш при неподвижной камере. Полёт начинается после неблокирующего GPU fence; UI отдельно показывает подготовку, исключая её из FPS. Если готовому кэшу требуется обновление после задержки, Rust завершает его в пределах максимального обычного шага камеры. Предел рассчитан из геометрии атласа, скорости полёта и clamp 100 мс, поэтому учитывает ultrawide. Большие скачки сохраняют ограниченный fallback. Холодный бюджет не увеличен, плотность 1.5, разрешение, итерации и AA не снижены. При недоступном необязательном кэше сохраняется полноэкранный рендер; маленькие холсты больше не зависают в подготовке.

## Проверка установленных Safari и Firefox

Apple M3 Max, Western armada, 2559×1358, 16384 итерации, AA2, старт 10^30. Настоящие приложения Safari 27.0 и Firefox 155.0.1, последовательный ABBA: original JS → WASM worker → WASM worker → original JS. Все четыре прохода используют свежие canvas. JS начинает с исходным холодным кэшем; WASM готовит его до полёта, время подготовки приведено отдельно.

| Браузер / участок | JS, два прохода | WASM, два прохода | Подготовка WASM |
| --- | ---: | ---: | ---: |
| Safari, 8 секунд | 30.88 / 28.50 FPS | 63.81 / 63.69 FPS | 567 / 563 мс |
| Safari, повтор 4 секунды | 20.91 / 20.92 FPS | 62.21 / 62.89 FPS | 576 / 550 мс |
| Firefox, 4 секунды | 119.13 / 119.97 FPS | 120.02 / 120.03 FPS | 409 / 394 мс |

В Safari на восьмисекундном участке отношение средних составляет около **2.15× (+115% FPS)**. В коротком участке преимущество больше, поскольку оригинальный JS ещё не успевает включить кэш; на восьмисекундном он включился через 6.55–7.03 с. В WASM ни один опубликованный sample не показал потери кэша. В Firefox оба движка достигают примерно 120 FPS, проблема запуска здесь не воспроизвелась. Это не подтверждение исправления на M1 Pro или RTX 5070 Ti: этих GPU в данном тесте нет.

FPS здесь — частота отправки кадров, не число физически показанных GPU кадров. Состояние worker публикуется примерно раз в 250 мс; короткие переходы между публикациями могут не попасть в отчёт. Safari и Firefox не предоставили аппаратный GPU timer. Холст имеет указанный renderbuffer, но уменьшен CSS для отчёта, поэтому compositor отличается от полноэкранного UI. Guided-фильтрация исходных движков различается: JS оставлен со своей адаптивной плотностью и старым шейдером, WASM сохраняет нашу полную плотность и AA. Эти цифры сравнивают реальные режимы, а не изолированную скорость языка.

Исходные отчёты: [Safari 8 с](benchmarks/safari-27-runtime-flight.json), [Safari 4 с](benchmarks/safari-27-runtime-flight-short.json), [Firefox](benchmarks/firefox-155-runtime-flight.json). Воспроизведение при запущенном `npm run dev`: `/scripts/profiles/runtime.html?width=2559&height=1358&depth=30&duration=8000`. Окно должно оставаться видимым; другие GPU-тесты следует остановить.

[Дополнительный стартовый прогон Chromium](benchmarks/chromium-153-runtime-flight-startup.json) также не показал потери подготовленного WASM-кэша. Однако повторы сильно разошлись: WASM 329/202 FPS, JS 94/20 FPS; JS успел прогреться только в первом проходе. Причина всей вариации не установлена, поэтому по этому прогону не заявляется стабильный процент ускорения или отсутствие регрессии на других устройствах.

# Полный перенос CPU-рендерера в WASM (предыдущий этап)

Камера, движение по маршруту, подготовка uniform, кольцевой кэш, temporal AA и цикл выдачи draw-команд перенесены в Rust. Орбита/BLA и WebGL работают в одном OffscreenCanvas worker. Память WASM фиксирована на 256 MiB при запуске; resizable buffer и рабочий рост памяти удалены. Direct upload использует постоянные views с offset, без промежуточных копий орбиты. GPU-память выделяется отдельно.

Проверки переноса сравнивают все параметры и команды 640 кадров кольцевого кэша (включая FullHD, 4K и принудительное разбиение полос) и 80 кадров temporal AA со старым планировщиком после преобразования uniform в float32. Нативные проверки считают выделения памяти на прогретых кадрах. Эталон JS со своими оригинальными шейдерами сохранён отдельно и не изменяется переносом.

В редких координатах `exp2` в WASM и платформенный `Math.pow(2,x)` V8 расходятся на 1 ULP. Ядро использует быстрый `exp2`; дорогое воспроизведение платформенных ошибок округления не добавлено. Операции над целыми проверяются точно, влияние преобразования масштаба ограничено и тестируется отдельно.

Новый A/B измеряет полный кадр: JS строит камеру и RenderView, WASM вызывает `render_frame(mode=1)`. CPU-время включает подготовку и выдачу WebGL-команд; GPU-время измеряется аппаратными queries. ABBA-прогоны последовательны, прогрев дожидается завершения GPU; worker основного canvas приостановлен. Сам benchmark использует один поток для обоих движков, поэтому не приписывает WASM преимущества отдельного расписания worker.

### Исправление начала измерения

Встроенный тест выявил устаревший первый rAF timestamp после синхронного `readPixels`: например, GPU-прогрев длился 191 мс, первый timestamp отставал на 193 мс, а следующий интервал составил 191.7 мс. Это ошибочно включало прогрев в секундный полёт, давало скачок камеры и fallback на втором кадре. Теперь после ожидания GPU оба движка пропускают один rAF без рендера, затем сбрасывают часы и начинают измерение. Сам runtime полёта не выполняет синхронный `readPixels`. Отчёт сохраняет возраст timestamp, rAF gaps и список fallback-кадров; нулевые значения CPU-медианы из-за точности таймера не трактуются как нулевая стоимость.

# Измерения и решения — 24 сентября 2026

Текущее приложение упрощено до двух движков: **WASM SIMD + GPU** и **JavaScript + GPU**. Scalar-сборка, «Авто» и переключение шейдеров удалены. Ниже сохранён исторический отчёт выбора оптимизаций; старые JSON-файлы документируют этот эксперимент, а не текущие варианты запуска. JS теперь использует сохранённые исходные шейдеры из опубликованной сборки, WASM — наши. Старое сравнение ниже с одним общим GPU-рендерером не описывает эту новую пару.

## Новое сравнение с исходными JS-шейдерами

[Полный JSON](benchmarks/chromium-153-original-js-vs-wasm.json), Chromium 153 / ANGLE Metal / Apple M3 Max, 24 сентября 2026. Два отдельных renderer работают последовательно. JS использует исходные строки опубликованного Burning Ship shader и исходную политику кэша. Численные выражения исходных shader strings сверены с оригинальным bundle; адаптирован только WebGL 2 интерфейс. Split-screen отсутствует.

| Измерение | JS + исходные шейдеры | WASM SIMD + GPU |
| --- | ---: | ---: |
| Опорная орбита, Worker, 576 бит / 16384 итерации | 22.30 мс | 16.10 мс |
| Полный ответ Worker | 22.40 мс | 16.10 мс |
| GPU без кэша, 320×200, AA2, 10^120 | 6.366 мс | 6.373 мс |
| Полёт Full HD, 10^30 → 10^30.55 | 218.6 FPS | 201.6 FPS |
| Полёт Full HD, 10^115 → 10^115.55 | 226.5 FPS | 226.1 FPS |

CPU-расчёт быстрее в **1.39×**, его время уменьшилось на **27.8%**. Ускорение GPU относительно настоящих исходных шейдеров не подтвердилось: пять сцен дали отношения JS/WASM примерно 0.97–1.01×. Выигрыша FPS также нет: в этом прогоне WASM ниже на 7.8% при 10^30 и практически равен JS при 10^115. Это результаты двух секундных серий на движок в порядке ABBA, а не долгосрочная оценка стабильности или универсальное ускорение.

FPS считает успешные вызовы render на rAF и ограничен расписанием браузера. GPU-прогрев и предыдущий проход синхронно завершаются до начала замера. Одинаковые настройки полёта: 1920×1080, AA2, 16384 итерации, 0.55 log10/с. В guided режиме фильтрация кэша различается: исходный JS сохраняет свой фильтр и адаптивную плотность; WASM сохраняет плотность 1.5 и дополнительное AA. Поэтому FPS сравнивает фактические режимы, а не гарантированно одинаковые пиксели. Равенство качества и пикселей проверяется отдельно без кольцевого кэша.

Все проверки завершились с `checks.passed=true`: опорные массивы совпали побайтово, пять полноэкранных сцен дали **0 отличающихся RGBA-каналов**, повторное использование кэша, temporal AA, отмена Worker и восстановление обоих renderer прошли проверки. При восстановлении original было найдено расхождение палитры до 1 LSB: лишнее сложение с uniform hue=0 меняло GPU-округление. Стандартная WASM-палитра теперь использует исходное дерево выражений. Node/TypeScript: **55/55**; production build прошёл.

### Большие экраны и память

В WASM удалён искусственный предел кольцевого атласа 24 млн texels, который отключал кэш при 1920×1080 (нужно 30 040 381 texels). Угловые полосы теперь раскладываются в несколько физических блоков при ограничении ширины текстуры. 4K использует атлас 10386×10353 — около 410 MiB RGBA8, сохраняя плотность 1.5. Учитываются реальные лимиты GPU и ошибки выделения памяти; при невозможности создать кэш используется полноценный прямоугольный рендер без снижения разрешения.

До/после изменения упаковки и принудительного разбиения полос пиксели совпали на тестовых сценах 320×200, 1280×720 и 1920×1080; 4K-кэш также проверен реальным WebGL-рендером. Эти изменения устраняют отключение кэша в нашей предыдущей версии и не означают такой же прирост относительно исходного JS, где уже был свой кэш с адаптивной плотностью.

## Предыдущий замер с общим GPU-рендерером (история)

Свежий прогон в том же Chromium 153 / Apple M3 Max: [полный JSON](benchmarks/chromium-153-two-engines-fps.json). Western armada, 576 бит, 16384 итерации; медиана 9 расчётов в Worker после прогрева.

| Измерение | JavaScript + GPU | WASM SIMD + GPU |
| --- | ---: | ---: |

Точность, кольцевой кэш, temporal AA, отмена Worker и восстановление GPU прошли встроенные проверки (`checks.passed=true`); опорные массивы и проверенные пиксели JS/WASM совпали. Текущий набор Node/TypeScript: 52 теста.

Полные данные: [браузер](benchmarks/chromium-153-apple-m3-max.json), [Node 24/V8](benchmarks/node-24-apple-m3-max.json).

По 2 прогрева и 9 измерений каждого варианта, варианты чередуются. Медианы ниже — время одного расчёта. p95 при 9 измерениях фактически является максимумом выборки; это не оценка долгосрочного хвоста задержек. GPU измерен через `EXT_disjoint_timer_query_webgl2`, без подмены временем `requestAnimationFrame`. Компиляция и прогрев исключены. Энергопотребление не измерялось.

CPU: Western armada, 576 бит координат + 32 рабочих бита, лимит 16384, фактическая длина опорной орбиты 12807. GPU: 320×200, 16384 итерации, 2 одинаковых пространственных сэмпла, без кольцевого кэша в сравнении шейдеров.

## CPU и память

| Вариант | Медиана, мс | p95, мс | Ускорение относительно JS |
| --- | ---: | ---: | ---: |
| JS BigInt | 20.20 | 26.60 | 1.00× |
| WASM scalar | 16.00 | 16.50 | 1.26× |
| WASM SIMD | 15.60 | 16.30 | 1.29× |
| WASM SIMD через worker, включая обмен | 15.80 | 16.40 | — |

SIMD относительно scalar дал 2.6% по медиане этого прогона; в предыдущих прогонах разница была около 0–2%. Поэтому большой дополнительный выигрыш от SIMD не заявляется. SIMD действительно присутствует в бинарнике: независимые столбцы BLA-матриц вычисляются через `f64x2.mul/add`; без relaxed SIMD и FMA. После этого сравнения в приложение оставлены только SIMD и JS.

`toResizableBuffer()` реально доступен и использован, буфер имеет `resizable=true`. Прогретая WASM memory — 2 424 832 байта (~2.31 MiB), без роста на повторных задачах. Это размер линейной WASM-памяти, а не всей вкладки/GPU. В бинарнике initial memory 2 MiB, maximum 256 MiB. Нативный allocator probe подтверждает отсутствие выделений внутри `step`, включая лимит 65536 итераций.

Орбита/BLA копируются в возвращаемый пул transferable ArrayBuffer. GPU upload остаётся отдельной операцией: zero-copy не заявляется. Общая задержка worker на целевой точке близка к локальному расчёту; перенос всего renderer в worker или shared memory не включён и не выдаётся за измеренное улучшение. Сравнение этих альтернатив отложено: сейчас оно потребовало бы усложнить владение ресурсами ради небольшой части общей задержки.

WASM не быстрее JS на любой разрядности. В стресс-проверке постоянной орбиты (-1,-1), **4096 бит / 4096 итераций**, scalar worker занял ~253 мс, JS ~37 мс: школьное умножение Rust-ядра уступает V8 на очень длинных числах. UI сохраняет явный JS backend для таких задач. Это ограничение текущего алгоритма длинного умножения; автоматический выбор backend по разрядности не реализован.

## GPU (историческая адаптированная baseline)

В этой таблице baseline не был дословным исходным шейдером: он содержал добавленные повторные чтения орбиты. Поэтому эти проценты нельзя считать выигрышем относительно опубликованного JS-оригинала. Для нового сравнения исходные shader strings восстановлены напрямую из bundle; оригинальные FE→float, carried orbit и texelFetch уже были оптимизированы автором.

| Сцена | Базовый, мс | Оптимизированный, мс | Отношение скоростей |
| --- | ---: | ---: | ---: |
| Обзор / direct | 10.159 | 10.143 | 1.00× |
| Western 10^10 / float | 0.685 | 0.574 | 1.19× |
| Western 10^30 / FE | 3.787 | 3.571 | 1.06× |
| Western 10^90 / FE | 2.573 | 2.519 | 1.02× |
| Western 10^120 / FE | 7.003 | 6.317 | 1.11× |

На всех пяти сценах **0 отличающихся RGBA-каналов** между базовым и принятым оптимизированным шейдером; при смене опорной орбиты JS→WASM также 0 отличий. Это измерение на одном GPU/драйвере, не обещание побитового равенства между разными GPU.

Приняты целочисленное выравнивание BLA и переиспользование чтения realOrbit в Celtic-ветке. **Константная специализация fold=1/celtic=0 отклонена**: даже direct-режим дал 1792 отличающихся пикселя из 64000, поэтому расхождение нельзя было объяснить BLA. При отключении только этой специализации совпадение восстановилось. Вероятная причина — другое округление после оптимизаций компилятора GPU; точный машинный код драйвера не исследовался. Её более быстрые результаты не включены в таблицу.

Кольцевой кэш сравнен отдельно: базовый/оптимизированный кадры совпадают, при повторе неподвижного кадра пересчитывается 0 строк; при шаге logScale −0.02 — 8 строк вместо 745 строк начального заполнения. Начальное заполнение распределено на 24 кадра с полноценным fallback. Плотность 1.5 сохранена; качество автоматически не уменьшается.

Temporal AA использует исходный центрированный jitter, накопление и перепроекцию истории. При AA=3 оба варианта достигают итогового кадра за 3 шага, пиксели после сброса/повтора и восстановления контекста совпадают.

## Надёжность и воспроизведение

- 64 Node/TypeScript-теста, 9 Rust-тестов, `cargo clippy -- -D warnings`, production build и проверка diff проходят.
- Scalar/SIMD совпадают с независимым BigInt-эталоном побайтно по всем пяти массивам на 18 постоянных входных наборах каждый. Дополнительно во время разработки проверены 2535 grid cases и 180 независимых adversarial cases.
- Проверены отрицательные shifts, округления, оси/fold/celtic, отмена, повторные вычисления, `memory.grow`, восстановление контекста и накопление AA.
- Настоящий Worker получил замену/отмену через 5–6 мс после старта тяжёлой задачи. Устаревшие результаты не опубликованы; новый ответ получен через 2–2.5 мс для WASM и 2.9–3.7 мс для JS после сигнала. Проверка обходит клиентский фильтр id.
- Реальная кнопка диагностики главного canvas также прошла потерю/восстановление WebGL: изображение вернулось, ошибок в консоли нет.

Встроенный JSON-отчёт завершился с `checks.passed=true`. Для повтора: `npm ci`, `npm run dev`, кнопка «Проверить точность и скорость». Native/Node: `npm test`, `npm run test:rust`, `npm run bench`.

Порт предназначен прежде всего для desktop Chromium. Исходное iOS-разбиение одной пиксельной орбиты на несколько draw-пакетов не перенесено; Safari/iOS, другие GPU и длительные энергетические профили не проверены. Все итерации, пространственное разрешение и заданный бюджет AA сохраняются; снижения качества для получения указанных ускорений нет.
