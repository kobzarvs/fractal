# Измерения и решения — 24 сентября 2026

Текущее приложение упрощено до двух движков: **WASM SIMD + GPU** и **JavaScript + GPU**. Scalar-сборка, «Авто» и переключение шейдеров удалены. Ниже сохранён исторический отчёт выбора оптимизаций; старые JSON-файлы документируют этот эксперимент, а не текущие варианты запуска. Текущий benchmark сравнивает только WASM SIMD с JS и проверяет один общий GPU-рендерер.

## Среда и методика

Apple M3 Max, macOS 26.7, встроенный Chromium 153.0.0.0, ANGLE / Metal. Отдельный Google Chrome недоступен через браузерный инструмент; эти результаты относятся к указанному Chromium. Полные данные: [браузер](benchmarks/chromium-153-apple-m3-max.json), [Node 24/V8](benchmarks/node-24-apple-m3-max.json).

По 2 прогрева и 9 измерений каждого варианта, варианты чередуются. Медианы ниже — время одного расчёта. p95 при 9 измерениях фактически является максимумом выборки; это не оценка долгосрочного хвоста задержек. GPU измерен через `EXT_disjoint_timer_query_webgl2`, без подмены временем `requestAnimationFrame`. Компиляция и прогрев исключены. Энергопотребление не измерялось.

CPU: Western armada, 576 бит координат + 32 рабочих бита, лимит 16384, фактическая длина опорной орбиты 12807. GPU: 320×200, 16384 итерации, 2 одинаковых пространственных сэмпла, без кольцевого кэша в сравнении шейдеров.

## CPU и память

| Вариант | Медиана, мс | p95, мс | Ускорение относительно JS |
| --- | ---: | ---: | ---: |
| JS BigInt | 20.20 | 26.60 | 1.00× |
| WASM scalar | 16.00 | 16.50 | 1.26× |
| WASM SIMD | 15.60 | 16.30 | 1.29× |
| WASM SIMD через worker, включая обмен | 15.80 | 16.40 | — |

SIMD относительно scalar дал 2.6% по медиане этого прогона; в предыдущих прогонах разница была около 0–2%. Поэтому большой дополнительный выигрыш от SIMD не заявляется. SIMD действительно присутствует в бинарнике: независимые столбцы BLA-матриц вычисляются через `f64x2.mul/add`; без relaxed SIMD и FMA. После этого сравнения в приложение оставлены только SIMD и JS.

`toResizableBuffer()` реально доступен и использован, буфер имеет `resizable=true`. Прогретая WASM memory — 2 424 832 байта (~2.31 MiB), без роста на повторных задачах. Это размер линейной WASM-памяти, а не всей вкладки/GPU. В бинарнике initial memory 2 MiB, maximum 256 MiB. Нативный allocator probe подтверждает отсутствие выделений внутри `step`, включая лимит 65536 итераций.

Орбита/BLA копируются в возвращаемый пул transferable ArrayBuffer. GPU upload остаётся отдельной операцией: zero-copy не заявляется. Общая задержка worker на целевой точке близка к локальному расчёту; перенос всего renderer в worker или shared memory не включён и не выдаётся за измеренное улучшение. Сравнение этих альтернатив отложено: сейчас оно потребовало бы усложнить владение ресурсами ради небольшой части общей задержки.

WASM не быстрее JS на любой разрядности. В стресс-проверке постоянной орбиты (-1,-1), **4096 бит / 4096 итераций**, scalar worker занял ~253 мс, JS ~37 мс: школьное умножение Rust-ядра уступает V8 на очень длинных числах. UI сохраняет явный JS backend для таких задач. Это ограничение текущего алгоритма длинного умножения; автоматический выбор backend по разрядности не реализован.

## GPU

| Сцена | Базовый, мс | Оптимизированный, мс | Отношение скоростей |
| --- | ---: | ---: | ---: |
| Обзор / direct | 10.159 | 10.143 | 1.00× |
| Western 10^10 / float | 0.685 | 0.574 | 1.19× |
| Western 10^30 / FE | 3.787 | 3.571 | 1.06× |
| Western 10^90 / FE | 2.573 | 2.519 | 1.02× |
| Western 10^120 / FE | 7.003 | 6.317 | 1.11× |

На всех пяти сценах **0 отличающихся RGBA-каналов** между базовым и принятым оптимизированным шейдером; при смене опорной орбиты JS→WASM также 0 отличий. Это измерение на одном GPU/драйвере, не обещание побитового равенства между разными GPU.

Приняты целочисленное выравнивание BLA и переиспользование чтения realOrbit в Celtic-ветке. **Константная специализация fold=1/celtic=0 отклонена**: даже direct-режим дал 1792 отличающихся пикселя из 64000, поэтому расхождение нельзя было объяснить BLA. При отключении только этой специализации совпадение восстановилось. Вероятная причина — другое округление после оптимизаций компилятора GPU; точный машинный код драйвера не исследовался. Её более быстрые результаты не включены в таблицу.

Кольцевой кэш сравнен отдельно: базовый/оптимизированный кадры совпадают, при повторе неподвижного кадра пересчитывается 0 строк; при шаге logScale −0.02 — 8 строк вместо 745 строк начального заполнения. Начальное заполнение распределено на 24 кадра с полноценным fallback. Плотность 1.5 сохранена; качество автоматически не уменьшается.

Temporal AA использует исходный центрированный jitter, накопление и перепроекцию истории. При AA=3 оба варианта достигают итогового кадра за 3 шага, пиксели после сброса/повтора и восстановления контекста совпадают.

## Надёжность и воспроизведение

- 64 Node/TypeScript-теста, 9 Rust-тестов, `cargo clippy -- -D warnings`, production build и проверка diff проходят.
- Scalar/SIMD совпадают с независимым BigInt-эталоном побайтно по всем пяти массивам на 18 постоянных входных наборах каждый. Дополнительно во время разработки проверены 2535 grid cases и 180 независимых adversarial cases.
- Проверены отрицательные shifts, округления, оси/fold/celtic, отмена, повторные вычисления, `memory.grow`, восстановление контекста и накопление AA.
- Настоящий Worker получил замену/отмену через 5–6 мс после старта тяжёлой задачи. Устаревшие результаты не опубликованы; новый ответ получен через 2–2.5 мс для WASM и 2.9–3.7 мс для JS после сигнала. Проверка обходит клиентский фильтр id.
- Реальная кнопка диагностики главного canvas также прошла потерю/восстановление WebGL: изображение вернулось, ошибок в консоли нет.

Встроенный JSON-отчёт завершился с `checks.passed=true`. Для повтора: `npm ci`, `npm run dev`, кнопка «Проверить точность и скорость». Native/Node: `npm test`, `npm run test:rust`, `npm run bench`.

Порт предназначен прежде всего для desktop Chromium. Исходное iOS-разбиение одной пиксельной орбиты на несколько draw-пакетов не перенесено; Safari/iOS, другие GPU и длительные энергетические профили не проверены. Все итерации, пространственное разрешение и заданный бюджет AA сохраняются; снижения качества для получения указанных ускорений нет.
